# «Арена переговоров» — техническая документация

Документ описывает опубликованную реализацию проекта: архитектуру, технологии, конфигурацию, локальный запуск и пример развёртывания на собственном сервере. Краткое описание для жюри — в [PROJECT_DESCRIPTION.md](PROJECT_DESCRIPTION.md), быстрый локальный старт — в [README.md](README.md).

## 1. Архитектура

```text
Браузер
  └─ Next.js / React (интерфейс, распознавание речи, воспроизведение аудио)
       └─ /api/v1/* → внутренний прокси Next.js
            └─ FastAPI (сценарии, сессии, движок, отчёты, обучение, peer-review)
                 ├─ PostgreSQL 16 (пользователи, диалоги, отчёты, проверки)
                 └─ Gemini API, опционально (текст оппонента, пояснения, TTS)
```

Веб-интерфейс по умолчанию обращается к API по тому же домену: правило в `apps/web/next.config.ts` перенаправляет `/api/v1/*` на `INTERNAL_API_URL` (локально — `http://127.0.0.1:8000`, в Docker-сети — `http://api:8000`). Ключ Gemini хранится только в окружении сервера API и не передаётся в переменные `NEXT_PUBLIC_*`.

Основной принцип: **серверный движок является источником истины**. Он определяет состояние переговоров, допустимость условий, исход и оценку. LLM получает ограниченный публичный контекст и директиву, после чего формулирует человеческую реплику; ответ проверяется, а при ошибке используется резервный вариант. Скрытые интересы и границы ролей не публикуются в API.

### Поток одной тренировки

1. Интерфейс запрашивает публичный брифинг и создаёт сессию через `POST /api/v1/sessions`.
2. Реплика участника поступает в `POST /api/v1/sessions/{id}/messages`; движок классифицирует её, обновляет состояние и определяет действие оппонента.
3. Опциональный Gemini формулирует ответ по директиве движка. Числовые условия и тип действия проверяются; при сбое применяется детерминированный ответ.
4. Сессия и сообщения сохраняются в PostgreSQL. При завершении рубрика рассчитывает отчёт и сохраняет его вместе с подтверждающими цитатами.
5. Пользователь видит отчёт сразу; повторная попытка связывается с предыдущей для сравнения. Взаимная проверка запускается отдельно и не меняет автоматический балл.

## 3. Сценарии, оценка и учебные механики

Два базовых сценария заданы версионируемыми JSON-файлами. Тематические варианты «случайного» режима строятся из проверенных семейств сценариев: меняются роли, контекст, задачи и диапазоны условий, но сохраняется корректная экономика сделки (включая BATNA, границы и область возможного соглашения). Пользовательский конструктор также опирается на валидированный шаблон, а не принимает произвольные скрытые лимиты из браузера.

Автоматическая рубрика рассчитана на 100 баллов: подготовка и защита интересов — 20, качество процесса — 25, создание и обмен ценностью — 20, качество результата — 25, отношения и деловой тон — 10. Штрафы применяются отдельно. Отчёт содержит исход, баллы по критериям, цитаты из диалога, проверку задач брифинга, зоны роста и альтернативные реплики. Gemini может обогатить словесное объяснение, но не меняет числовой результат.

Модель взаимной проверки вдохновлена «Школой 21», без организационной связи со Сбером. После собственного автоматического отчёта участник проверяет чужую анонимизированную сессию по той же рубрике; если подходящей сессии нет, система выдаёт учебный эталон. Для первой проверки зарегистрированного участника предусмотрена калибровка. Система сопоставляет выставленные баллы с автоматическим разбором, проверяет наличие ссылок на реплики, пояснений и альтернативной формулировки, рассчитывает рейтинг проверяющего и поддерживает разбор спорных оценок. Ожидание рецензента не блокирует отчёт, повторную попытку или завершение тренировки.

Персональная траектория использует историю сессий, карту навыков и заданную пользователем цель, чтобы предлагать следующий кейс и мини-упражнение. У зарегистрированного участника история хранится на сервере; для гостя домашние рекомендации могут опираться на последние попытки в браузере.

### Голосовой режим

Режим «звонок» держит микрофон активным, отслеживает паузу после завершённой мысли, отправляет распознанный текст как обычную реплику и воспроизводит потоковое аудио оппонента. Пользователь может снова говорить без нажатия кнопки на каждом ходе. Это **не WebRTC и не истинная передача двух независимых аудиопотоков одновременно**: ход переговоров по-прежнему проходит через HTTP API. Распознавание зависит от поддержки Web Speech API и разрешения на микрофон; естественный голос оппонента требует доступного Gemini TTS. Есть резервный последовательный голосовой интерфейс и полноценный текстовый режим.

В звонке на сервер отправляется распознанный текст, а не непрерывная запись микрофона. Отдельная функция сохранения пользовательской записи работает по согласию и выбранному сроку хранения (24 часа или 30 дней); просроченные записи очищаются при запуске API и периодически во время работы.

## 4. Данные, API и безопасность

PostgreSQL хранит учётные записи и сессии входа, версии пользовательских черновиков сценариев, переговорные сессии и сообщения, отчёты, учебные данные, задания взаимной проверки и, при отдельном согласии, голосовые записи. Базовые кейсы поставляются JSON-файлами, а случайный каталог создаётся из проверенных шаблонов. Схему базы необходимо обновлять командой `alembic upgrade head` **до** запуска новой версии API. Не следует заменять PostgreSQL SQLite для обычного локального или серверного запуска: актуальные миграции рассчитаны на PostgreSQL.

Ключевые HTTP-маршруты:

| Маршрут | Назначение |
| --- | --- |
| `GET /api/v1/scenarios`, `GET /api/v1/scenario-catalog` | Брифинги и фильтруемый каталог кейсов. |
| `POST /api/v1/sessions`, `POST /api/v1/sessions/{id}/messages` | Создание сессии и ход переговоров. |
| `POST /api/v1/sessions/{id}/complete`, `GET /api/v1/sessions/{id}/report` | Завершение и сохранённый отчёт. |
| `POST /api/v1/sessions/{id}/retry`, `GET /api/v1/sessions/{id}/comparison` | Повтор и сравнение попыток. |
| `GET /api/v1/peer-reviews/next`, `POST /api/v1/peer-reviews` | Назначение и отправка взаимной проверки. |
| `GET /api/v1/me/learning`, `GET /api/v1/me/motivation` | Личная траектория и мотивационные механики. |
| `GET /health/ready`, `GET /health/dependencies` | Готовность базы и состояние внешних зависимостей. |

Полная спецификация запросов доступна в `/docs` при `APP_ENV=development`; в production Swagger/OpenAPI отключён. Защита включает проверку владельца данных, HttpOnly-cookie для сессии, CSRF-токен для изменений от имени пользователя, TrustedHost/CORS, ограничения размера запроса и частоты обращений, CSP на веб-слое. Предел частоты реализован в процессе API; при масштабировании на несколько экземпляров понадобится общий механизм лимитирования.

## 5. Локальный запуск

Нужны Python 3.12, Node.js 22 с npm и Docker с Compose v2. Из корня чистого клона:

```bash
docker compose up -d --wait postgres
```

Запуск API в отдельном терминале (Linux/macOS):

```bash
cd apps/api
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -e .
export DATABASE_URL='postgresql+psycopg://arena:arena_local_only@localhost:5432/arena'
alembic upgrade head
python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Windows PowerShell:

```powershell
cd apps/api
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e .
$env:DATABASE_URL = 'postgresql+psycopg://arena:arena_local_only@localhost:5432/arena'
.\.venv\Scripts\alembic.exe upgrade head
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Затем в новом терминале из корня репозитория:

```bash
cd apps/web
npm ci
npm run dev
```

Откройте <http://localhost:3000>. Готовность API: <http://127.0.0.1:8000/health/ready>. В локальном режиме ключ Gemini не обязателен: оставьте `GEMINI_API_KEY` пустым, чтобы проверить текстовые переговоры и отчёт через резервный режим. Для голосового ответа укажите **свой** ключ только в окружении API. Если API выключен, интерфейс может показать встроенный демонстрационный режим — его отчёт не следует путать с серверной оценкой.

## 6. Развёртывание на VPS с Docker

Ниже — воспроизводимая схема для одного Linux-сервера с установленными Docker Engine, Compose v2 и внешним HTTPS reverse proxy. В репозитории есть Dockerfile для обоих приложений, но `compose.yaml` поднимает **только PostgreSQL**; конфигурация домена, TLS и прокси зависит от конкретного VPS и в репозиторий не включена.

1. Клонируйте проект и подготовьте конфигурацию PostgreSQL:

   ```bash
   git clone https://github.com/Titablya/nii-garage.git
   cd nii-garage
   cp .env.example .env
   ```

   В локальном `.env` замените `POSTGRES_PASSWORD` на сильный уникальный пароль и задайте `POSTGRES_PORT=127.0.0.1:5432`, чтобы база не слушала внешний сетевой интерфейс. Не публикуйте `.env` и не используйте примерный пароль в production.

2. Создайте вне репозитория файл окружения API, например `/etc/nii-garage/api.env`, с правами доступа только у администратора. Минимально потребуются:

   ```dotenv
   DATABASE_URL=postgresql+psycopg://arena:<URL_ENCODED_DB_PASSWORD>@postgres:5432/arena
   APP_ENV=production
   TRUSTED_HOSTS=api,localhost,127.0.0.1,<YOUR_DOMAIN>
   CORS_ORIGINS=https://<YOUR_DOMAIN>
   SESSION_COOKIE_SECURE=true
   GEMINI_API_KEY=
   ```

   Вместо угловых скобок подставьте значения своего сервера; специальные символы пароля в URL закодируйте. Для естественного голоса и генерации через Gemini заполните `GEMINI_API_KEY` только в этом серверном файле. Ключ не должен попадать в Git, логи или браузерные переменные.

3. Поднимите базу, соберите образы и примените миграции:

   ```bash
   docker compose up -d --wait postgres
   docker build -t nii-garage-api ./apps/api
   docker build -t nii-garage-web ./apps/web
   docker run --rm --network arena-negotiations_default \
     --env-file /etc/nii-garage/api.env \
     nii-garage-api alembic upgrade head
   ```

4. Запустите API и интерфейс в одной Docker-сети. Имя контейнера `api` важно: на него ссылается стандартная сборка Next.js через `INTERNAL_API_URL=http://api:8000`.

   ```bash
   docker run -d --name api --restart unless-stopped \
     --network arena-negotiations_default \
     --env-file /etc/nii-garage/api.env \
     -p 127.0.0.1:8000:8000 nii-garage-api

   docker run -d --name nii-garage-web --restart unless-stopped \
     --network arena-negotiations_default \
     -p 127.0.0.1:3000:3000 nii-garage-web
   ```

5. Настройте внешний reverse proxy: HTTPS-домен → `http://127.0.0.1:3000`. Откройте снаружи только 80/443; порты API, Web и PostgreSQL оставьте привязанными к loopback. Проверьте `curl http://127.0.0.1:8000/health/ready`, затем откройте HTTPS-сайт, создайте тестовую сессию и получите отчёт.

Перед обновлением сделайте резервную копию PostgreSQL и храните её вне контейнерного тома. Затем получите новую версию кода, пересоберите образы, примените миграции и только после этого замените контейнеры приложений. Не удаляйте volume `arena_postgres_data`: в нём находятся пользовательские данные. Для домена, сертификата и резервного копирования используйте выбранную инфраструктуру VPS; эти настройки не хранятся в публичном коде.

## 7. Переменные окружения и проверки

Примеры без секретов: [корневой `.env.example`](.env.example), [`apps/api/.env.example`](apps/api/.env.example) и [`apps/web/.env.example`](apps/web/.env.example). Основные параметры: `DATABASE_URL`, `GEMINI_API_KEY`, `GEMINI_MODEL`, `GEMINI_TTS_MODEL`, `APP_ENV`, `TRUSTED_HOSTS`, `CORS_ORIGINS`, `SESSION_COOKIE_SECURE`, `INTERNAL_API_URL`. `NEXT_PUBLIC_API_URL` обычно оставляют пустым для same-origin прокси. Если включаете `TRUST_PROXY_HEADERS`, доверяйте только собственному прокси, иначе можно подделать IP-адрес для лимитирования.

Проверки кода после изменений:

```bash
cd apps/api
python -m pip install -e ".[dev]"
python -m pytest

cd ../web
npm ci
npm run typecheck
node --test
npm run build
```

В текущем опубликованном снимке проходят 311 тестов API, 9 тестов веб-утилит и production-сборка Next.js. Эти проверки не заменяют ручной прогон переговоров и голосового режима в целевом браузере.
